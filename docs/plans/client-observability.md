# Optional client observability

## Current State

- Status: planned, not implemented or deployed. Jonny enabled Vercel Analytics and Speed Insights in the dashboard and selected coarse, anonymized route reporting (option A). He additionally wants slow research requests discoverable from the dashboard and attributable to attempt-level logs. Neither npm package is installed in this repository.
- The app is a Vite React Router SPA (`src/main.tsx` composes `BrowserRouter` and `App`). `/threads/new?q=...` can contain a prompt in the URL; `/threads/:threadId` contains an identifier; `/unlock` may carry a return URL. Browser telemetry is not a substitute for server `research_timing` assessment/extraction diagnostics.
- Existing `research_timing` at info already records `execution_ms`, `resolution_ms`, attempt totals and stage durations per completed request; `assessment_attempt` at debug records per-attempt latency, cap, stop, outcome and usage. The repeated slow pattern is a first attempt hitting 1,200 output tokens with `max_tokens`/`missing_directive`, then a successful 1,600-cap retry. `missing_directive` can be a nested fragment found inside truncated outer JSON, not proof the model omitted the directive. With `LOG_LEVEL=info`, debug details of a finished request cannot be recovered afterward.
- The repository guide points to a current-state audit that is absent in this checkout; the archived plans remain reference for shipped route and privacy contracts.

## Decision

- Implement one optional **client UI** telemetry mount at `src/main.tsx`, outside domain/application, with a concrete Vercel adapter under `src/infrastructure/`. Avoid a generic event bus, domain port, server dependency, or custom research events. Install `@vercel/analytics` and `@vercel/speed-insights` and mount their React components only in that adapter, once per app. A no-op is the default; a non-secret, build-time opt-in `VITE_TELEMETRY_PROVIDER=vercel` in an approved Vercel environment selects the adapter. Production build alone does not imply Vercel. Failed telemetry loading/reporting must not block routes, auth, research, or rendering. A future provider replaces this composition seam, not business logic.
- Both `beforeSend` policies must allowlist known routes, remove all query strings and fragments, group `/threads/:threadId` under a route template, and drop unknown/sensitive paths. Treat `/threads/new` and `/unlock` as sensitive until verified safe; do not collect prompts, IDs, passphrases, answer text, provider payloads, or raw URLs. Speed Insights' `route` must be a normalized pattern, never the concrete thread ID. Confirm initial-load script requests and Referrer headers do not carry prompt or thread identifiers; add a portable referrer policy or exclude affected routes before production enablement if needed. No silent privacy fallback.
- Verify generic React package behavior on React Router SPA navigation; no manual duplicate pageview instrumentation. Web Analytics reports page/route usage and Speed Insights browser vitals, **not** assessor/provider duration. Do not promise or build an exact join from either client dashboard to a server invocation; do not send execution IDs, user prompts or high-cardinality correlation keys to analytics. Vercel **Observability → Functions → `POST /api/turn` → Logs**, or the equivalent bounded Logs lookup, is the primary slow-request investigation path. Vercel documents function latency/path breakdown as an Observability Plus feature; verify available dashboard capabilities read-only before relying on it. Use the invocation's platform Request ID to group the existing info-level `research_timing`, any new anomaly record, and any debug records already enabled at request time. Without per-request Observability features, a bounded time-window log batch is the fallback; do not claim a per-request analytics-to-logs link.
- Add a count-only assessment diagnostic for the actual ambiguity: on rejected/truncated structured output, classify whether the outer JSON object is incomplete, complete but lacks a directive, or complete with an invalid directive; optionally count fully parsed observation objects with a small cap. On accepted proposals, record bounded observation count (and not its text or refs) to assess output verbosity. Put low-cardinality shape/attempt fields on a single info-level **anomaly** record only for rejected/retried or slow assessment attempts; keep ordinary per-attempt debug logs. Do not log provider text, JSON fragments, questions, source IDs, support refs, thread IDs, raw payloads, exception text or URLs. Sanitize/clamp at the boundary; observers must not affect assessment. Do not change token caps, prompt, retries, parser acceptance, evidence, or SSE/durable contracts.
- A non-streaming assessment call cannot distinguish network/queue/prefill from generation time. Assessment streaming or a provider swap is deferred; do not claim that more logging will identify its provider-internal cause.
- No Vercel-side mutation (env var, deployment, dashboard action) without showing exact command, target and effect and receiving separate explicit approval. `npm install` is local project work; it does not activate collection in Production by itself.

## Open Questions

- Which implementation of portable Referrer-Policy best protects direct loads without changing unrelated embeds/navigation? Settle with a browser network test before P2 closes.
- Does the installed SDK version track React Router transitions automatically and support both `beforeSend` hooks as expected? Verify at implementation time; do not assume from generic framework docs.
- Is Observability Plus available on this Vercel project? Its function latency/path breakdown is documented as Plus-only. If absent, rely on narrow log windows and grouped Request IDs, not a nonexistent per-request analytics dashboard.
- The shape of future non-LLM research routing and any server-side observability provider remain outside this plan.
