## Decision

- Implement one optional **client UI** Analytics mount at `src/main.tsx`, outside domain/application, with a concrete Vercel adapter under `src/infrastructure/`. Avoid a generic event bus, domain port, server dependency, or custom research events. Install only `@vercel/analytics` and mount its React component only in that adapter, once per app. Speed Insights is deferred in prose only: the inspected v2.0.0 wrapper retains its script and route across sensitive SPA transitions, while its `beforeSend` contract does not establish control over the remote collector's independently constructed attribution or payload. A read-only inspection of a fetched remote script suggests `attribution.eventTarget`, but installed source alone does not prove the actual emitted fields or their safety. The no-identifiers contract therefore remains unverified. Do not install, mount, stub, or test that SDK in this implementation. A no-op is the default; a non-secret, build-time opt-in `VITE_TELEMETRY_PROVIDER=vercel` in an approved Vercel environment selects the adapter. Production build alone does not imply Vercel. Failed telemetry loading/reporting must not block routes, auth, research, or rendering. A future provider replaces this composition seam, not business logic.
- Analytics `beforeSend` must allowlist known routes, remove all query strings and fragments, group `/threads/:threadId` under a route template, and drop unknown/sensitive paths. Treat `/threads/new` and `/unlock` as sensitive until verified safe; do not collect prompts, IDs, passphrases, answer text, provider payloads, or raw URLs. Confirm initial-load script requests and Referrer headers do not carry prompt or thread identifiers; add a portable referrer policy or exclude affected routes before production enablement if needed. No silent privacy fallback.
- Verify generic React package behavior on React Router SPA navigation; no manual duplicate pageview instrumentation. Web Analytics reports page/route usage, **not** assessor/provider duration; deferred Speed Insights would report browser vitals only. Do not promise or build an exact join from either client dashboard to a server invocation; do not send execution IDs, user prompts or high-cardinality correlation keys to analytics. Vercel **Observability → Functions → `POST /api/turn` → Logs**, or the equivalent bounded Logs lookup, is the primary slow-request investigation path. Vercel documents function latency/path breakdown as an Observability Plus feature; verify available dashboard capabilities read-only before relying on it. Use the invocation's platform Request ID to group the existing info-level `research_timing`, any new anomaly record, and any debug records already enabled at request time. Without per-request Observability features, a bounded time-window log batch is the fallback; do not claim a per-request analytics-to-logs link.
- Profile the requested five stages explicitly in one server-side turn-local record: Brave search calls, page extraction, resolution, assessment, and synthesis. Preserve the existing timing fields and add only gaps that clarify wall time or meaningful subphases, rather than duplicating clocks. Use monotonic timers, bounded integer millisecond values, fixed stage names and count/max/cumulative for repeated calls; separately report wall spans where concurrent work occurs. For newly added subphase fields, an unentered phase is unmeasured (omit/null), not a zero-duration success; preserve existing zero-call stage counters for compatibility. Timers must cover success, rejection, interruption, timeout and failure without double emission or late callback writes. Do not sum nested/cumulative stages as if they partition `execution_ms`.
- Candidate subphases, only where separately measurable without a second fetch or changed behavior: Brave HTTP response versus response JSON/normalization; extraction URL/DNS safety, HTTP/redirect/header wait, bounded body, and text parsing/admission (record winner-only results under the outer 8s timeout); acquisition wall time around ranked search/parallel extraction; assessment provider attempt(s), parse, validation and retry; synthesis time to first output versus remaining generation/validation. Keep bounded aggregate counters, not per-URL/per-source timelines. Existing `extraction` failure phases and `assessment_profile` already cover part of this; measure first and avoid redundant instrumentation. Network/queue/prefill versus generation inside non-streaming assessment remains unknowable without a separate behavioral change. No raw URLs, text, query, source IDs or provider payloads in timing.
- Add a count-only assessment diagnostic for the actual ambiguity: on rejected/truncated structured output, classify whether the outer JSON object is incomplete, complete but lacks a directive, or complete with an invalid directive; optionally count fully parsed observation objects with a small cap. On accepted proposals, record bounded observation count (and not its text or refs) to assess output verbosity. Put low-cardinality shape/attempt fields on a single info-level **anomaly** record only for rejected/retried or slow assessment attempts; keep ordinary per-attempt debug logs. Do not log provider text, JSON fragments, questions, source IDs, support refs, thread IDs, raw payloads, exception text or URLs. Sanitize/clamp at the boundary; observers must not affect assessment. Do not change token caps, prompt, retries, parser acceptance, evidence, or SSE/durable contracts.
- No Vercel-side mutation (env var, deployment, dashboard action) without showing exact command, target and effect and receiving separate explicit approval. `npm install` is local project work; it does not activate collection in Production by itself.

### Timing contract

| Stage | Already measured | Profile further when useful |
| --- | --- | --- |
| Brave search | Per-call count, sum and max including HTTP + normalization | HTTP/header wait vs JSON parsing/normalization; search-round wall if calls overlap |
| Extraction | Per-call count, sum and max; categorized nonviable failure phase | Safe URL/DNS, fetch/redirect, bounded body, text parse/admission; acquisition wall across concurrent sources |
| Resolution | `resolution_ms` wall including search, extraction and assessment | Acquisition wall and remaining orchestration, without subtracting overlapping stage sums |
| Assessment | Per-call count/sum/max; attempt duration, tokens, parse and validation | Output shape, accepted observation count and whether time came from retries; provider-internal queue vs generation remains unmeasured |
| Synthesis | Per-call count/sum/max, first provider output and first server answer signal | Remainder to final validated answer / terminal preparation; never label server signal as browser paint |

These are server timings, not Vercel Speed Insights measurements. A timing summary belongs to the one invocation even on failure/interruption; missing new subphases stay explicitly unmeasured. Do not introduce per-source URLs, high-cardinality labels or another request identifier.
