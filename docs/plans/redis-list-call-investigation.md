## Decisions

Use the existing `thread_list_timing` fields (`ids_ms`, `records_ms`, `sort_ms`, `total_ms`, bounded counts and `max_record_ms`), not dashboard metric Sum as a single-request duration. **Trial proposal:** keep `listIds()` and its legacy migration serial (the measured IDs phase is small). After obtaining IDs, fetch current record/tombstone pairs via ordered `MGET` chunks with a provisional cap of eight IDs/16 keys. This caps key count, **not** response bytes: `threadV3Schema` does not impose a whole-record byte maximum. Before fixing a chunk size, check actual provider response limits and representative/worst-supported record sizes; if safe batch size requires new write limits, pause for owner approval rather than pretending the payload is bounded. For pairs both absent, batch the *legacy record checks* too; only valid legacy candidates perform their existing conditional migration and reread. Keep shared schema/source-identity validation, expiry/tombstone behavior, sorting and failure semantics. The installed `@upstash/redis` types expose `mget`; its response shape/deserialization must be fixture-verified before trusting it. A pipeline cannot know the index members until the first index response, so a literal one-round-trip list would need Lua or a new summary index; neither is part of this small change. Classify 129 non-returning IDs separately; do not remove members from counts alone. Before any live Vercel read, confirm project `prj_ce8rS67kx52XrVeuyL9QXLB2B0Hp` is `dorothy-ann` Production, then constrain inspection to a given deployment/Request ID and short time window; summarize only safe aggregates. No live logs were accessed in this plan.
