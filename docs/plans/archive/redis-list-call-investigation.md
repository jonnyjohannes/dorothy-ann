## Decisions

Use the existing `thread_list_timing` fields (`ids_ms`, `records_ms`, `sort_ms`, `total_ms`, bounded counts and `max_record_ms`), not dashboard metric Sum as a single-request duration. **Trial proposal:** keep `listIds()` and its legacy migration serial (the measured IDs phase is small). After obtaining IDs, fetch current record/tombstone pairs via ordered `MGET` chunks with a provisional cap of eight IDs/16 keys. This caps key count, **not** response bytes: `threadV3Schema` does not impose a whole-record byte maximum. Upstash documents `ERR max request size exceeded` for oversized read commands ([limit](https://upstash.com/docs/redis/troubleshooting/max_request_size_exceeded)); its SDK wraps non-OK JSON `error` as `UpstashError`. Use a narrowly identified error to split the chunk and finally fall back to existing single-record reads; propagate other errors without leaking keys or payloads. This provides bounded requests without claiming an absolute response-byte ceiling or changing accepted records. For pairs both absent, batch the *legacy record checks* too; only valid legacy candidates perform their existing conditional migration and reread. Keep shared schema/source-identity validation, expiry/tombstone behavior, sorting and failure semantics. The installed `@upstash/redis` client exposes `mget`; its ordered response and size-error shape were verified against a mocked REST response. A pipeline cannot know the index members until the first index response, so a literal one-round-trip list would need Lua or a new summary index; neither is part of this small change. Classify 129 non-returning IDs separately; do not remove members from counts alone. Before any live Vercel read, confirm project `prj_ce8rS67kx52XrVeuyL9QXLB2B0Hp` is `dorothy-ann` Production, then constrain inspection to a given deployment/Request ID and short time window; summarize only safe aggregates. Later bounded Production logs were inspected read-only, as recorded in Verification.
